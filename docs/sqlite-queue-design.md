# SQLite、并发保存与重复扫描设计

本文记录 SQLite 持久化、后台并发消费者和 `/scan` 的实现约束。

## 范围与默认值

- 持久化当前目录、文件索引、保存任务及失败重试记录。
- `DOWNLOAD_CONCURRENCY` 默认 `2`，必须是正整数，对应固定数量的异步消费者。
- 文件仍保存在 `DOWNLOAD_ROOT`，数据库默认位于 `DOWNLOAD_ROOT/.hamster.sqlite3`。
- 保留现有目录结构、`file_N` 命名、目录内去重、相册汇总和失败重试体验。
- 初版按单个机器人进程设计，数据库版本用 `PRAGMA user_version` 管理。

## 保存流程与线程边界

消息处理器确定目标目录并将任务写入数据库，唤醒消费者后返回。消费者原子领取
一条待执行文件任务，执行 Telegram 请求和本地保存，更新结果。相册批次负责
收集和汇总，文件任务允许并行执行，终态更新负责保证只启动一次批次汇总。

目标目录在入队时固定；相册在首个成员到达时固定目录并持久化收集窗口。后续
切换目录不改变已提交批次。保留约 1.5 秒的收集窗口，晚到的成员追加至原批次
并更新汇总。重试仅将失败项原子改回待执行，继续使用原目标目录。

Telegram 请求在事件循环中异步执行，所有消费者共享 API 限速器。复制、哈希、
目录扫描等阻塞操作在线程中执行。文件处理按消费者数量限制并发，扫描使用
一个专用的 `ThreadPoolExecutor(max_workers=1)`，避免长扫描占满文件处理线程。

SQLite 访问集中到一个模块，使用 `sqlite3`；连接在执行数据库操作的线程中
创建并关闭，不在线程间共享。扫描线程持有自己的连接。数据库使用短事务、
WAL 和有限锁等待；事务内不进行哈希、复制或网络等待。数据库及 WAL 文件应
位于本机持久化文件系统。

## 最小数据结构

- `chat_settings`：聊天当前目录及更新时间。
- `folders`：目录名称、下一个文件编号、首次索引是否完整、扫描代次和最近结果。
- `files`：相对路径、目录、SHA-256、大小、纳秒修改时间、落盘/缺失状态、最近见到的扫描代次。
- `batches`：聊天、原消息/相册、目标目录、收集窗口、汇总状态、消息 ID、重试标识与到期时间。
- `job_items`：批次、聊天和原消息、Telegram 文件标识、执行状态、次数、错误、临时/目标路径、关联文件及成功时的内容哈希。

必要约束和索引：文件相对路径唯一；接收消息按 `(chat_id, message_id)` 去重；
按目录和哈希查询文件；按任务状态和顺序领取待办。Telegram 文件标识可以
通过成功任务及关联文件建立快速查重索引，旧文件没有该信息时使用内容哈希。

历史目录可能有同内容的多个文件，因此 `(folder_id, sha256)` 使用普通索引，
不设唯一约束。导入时所有路径都保留，新保存通过最终提交协调避免新增副本。

## `/scan` 命令

- `/scan`：重新扫描 `DOWNLOAD_ROOT` 中的现有保存目录。
- `/scan <目录名>`：仅扫描指定的已有目录，名称沿用现有校验规则。
- 全局同一时间只允许一个扫描请求；首次自动导入和手动扫描共用同一协调器。
- 运行中再次发送 `/scan`，返回当前范围、阶段和进度，不排队、不再启动线程。
- 接单后立即回复，包含当前目录、检查/复用/更新/缺失/失败数量；结束后发送汇总。
- 重复触发时可以查询进度，首版不增加定时任务、扫描取消命令或逐文件通知。

目录查找和枚举也在线程中完成；命令处理器只做参数校验及接单。指定不存在的
目录时明确反馈，不因为扫描请求创建目录。扫描尚在准备时也算运行中，防止
两个命令同时通过检查。

首次自动导入使用相同流程，成功导入的目录在正常启动时不再自动全量重扫。
重启时发现首次索引未完成的目录则重新导入；普通手动重扫中断后保留原有效
索引，并记录中断结果，下一次 `/scan` 可继续利用已提交进度。

## 可重复执行的导入

1. 在工作线程中枚举根目录下的保存目录，逐个处理。当前存储结构是一层目录，
   首版只登记每个保存目录内的普通文件；遇到更深目录则报告跳过，不静默递归。
2. 排除数据库及其 WAL/SHM、程序管理的 `.saving-*` 临时项和符号链接。扫描
   对象是 `DOWNLOAD_ROOT`，不扫描代码仓库或 `telegram-bot-api` 缓存。
3. 以相对路径匹配已有记录。记录有效且大小、修改时间未变时复用哈希，只更新
   本次见到的扫描代次。旧记录缺少哈希时仍需计算。
4. 新增或变化文件流式计算 SHA-256，不整文件载入内存；哈希前后检查文件状态。
   读取失败、消失或读取期间变化的文件记录为失败，不登记为已验证的新内容。
   已有记录若被发现变化却无法校验，应失效其旧哈希，避免快速查重误用。
5. 小批量提交成功结果，例如每 100 条提交一次。更新只涉及文件系统索引字段，
   保留已关联的 Telegram 标识、来源消息、任务结果等现有业务信息。若同一路径
   的内容被替换，历史记录仍保留原内容哈希；快速查重必须比较历史哈希与当前
   实体哈希，仅有路径关联不代表旧 Telegram 文件仍对应现在的内容。
6. 完整枚举且所有文件校验成功后，在短事务中将本目录本轮未见到的已登记实体
   标记为缺失，并标记本轮完成。限定为实体文件记录，不涉及正在保存的临时项。
   扫描失败、取消或枚举不完整时不执行缺失标记，也不宣称索引完整。
7. 编号更新为现有数据库计数器和扫描所得最大 `file_N + 1` 中的较大值，绝不
   回退；保存时仍检查目标路径存在性，避免覆盖外部新增文件。

缺失文件保留索引和任务关联，只失去可复用资格；文件再次出现时可恢复记录。
历史重复内容不删除、不改名、不合并路径。空目录也登记。导入不会伪造旧文件
的 Telegram 文件标识、原消息或保存时间，无法恢复的字段保持未知。

首次从旧版升级时，扫描只能恢复磁盘上的信息。旧版内存中的当前目录选择和
失败按钮无法还原；未记录的聊天从 `default` 开始。升级后入库的新状态和重试
记录才具有跨重启恢复能力。

中断后重新执行时，已提交且未变化的文件不重新哈希，未提交部分重新处理。
这是文件级恢复，不需要持久化目录迭代器或哈希过程。外部程序直接改文件无法
获得事务快照；前后状态检查用于发现普通修改，连续外部写入时需再次扫描。

## 扫描与并发保存的协调

每个目录有一把由事件循环管理的异步锁，扫描和所有最终保存决策都必须经过它。
锁对象和正在扫描的目录集合仅在事件循环中访问，不交给线程。

扫描一个目录时：

1. 协调器将目录标记为扫描中，消费者暂不领取该目录的新任务。
2. 等待取得目录锁，再将该目录的扫描和索引更新提交给扫描线程。
3. 扫描线程退出并完成数据库提交后，协调器处理结果，释放目录锁、清除标记，
   然后唤醒保存消费者。错误路径也必须按这个顺序收尾。

已经开始的下载和临时文件复制可以继续；它们在最终保存前等待目录锁。临时项
被扫描排除。扫描持锁期间，该程序不会新增正式文件，扫描结果不会把刚落盘
但尚未登记的文件误判为孤立文件。其他目录不共用这把锁。

所有保存路径，包括 Telegram 标识命中的快速去重，也必须在目录锁内重新检查
目标文件和有效索引。哈希计算在锁外；同内容文件并发进入最终提交时，后进入
的任务查到前者的有效副本，清理自己的临时文件并标记为重复。

最终提交记录预期目标路径和哈希，再以同文件系统硬链接原子发布目标文件并
移除临时路径，最后提交文件与任务成功状态。硬链接创建不会覆盖已有路径；
下载目录所在文件系统需要支持硬链接。
进程重启后先校验并恢复已登记的中间状态，再开始首次索引及消费者执行，避免
扫描和恢复同时接管同一文件。文件系统操作与 SQLite 不是同一事务，恢复步骤
用于覆盖文件发布成功而数据库提交未完成的时间窗口。

首版采用目录级串行协调，扫描期间同目录的新落盘会等待；不增加逐文件锁或
并行扫描器。领取任务时跳过扫描中的目录，减少消费者无意义地占用处理名额。

## 线程进度、取消和关闭

扫描线程只负责文件系统和 SQLite；不直接调用 Telegram API、不操作 asyncio
锁、不修改共享任务字典。线程通过 `loop.call_soon_threadsafe` 提交不可变进度
快照，事件循环负责更新状态和回复。进度按时间节流，避免逐文件回调淹没循环。

每次请求有独立 `scan_id`，进度还有递增序号。协调器忽略不属于当前扫描、序号
过期或扫描结束后到达的回调，避免旧线程的延迟进度覆盖新状态。

取消等待扫描的协程不等于停止线程。协调器必须持有线程任务的强引用并保护其
不被连带取消。关闭时通过 `threading.Event` 请求停止；线程在枚举、文件读取
分块及提交边界检查停止信号，提交或回滚当前短事务后退出。

在确认线程实际退出前，不释放目录锁、不清除扫描中状态、不关闭仍被使用的
数据库连接、不启动第二次扫描。等待线程退出须异步进行，不能在事件循环上
调用阻塞的 `Future.result()` 或线程 join。文件最终提交的线程操作也遵循同样
的“实际完成后释放目录锁”规则。

进程被直接终止时，SQLite 保留已经提交的进度；下次启动将旧的进行中标记归为
中断，恢复保存中间状态，再按目录的首次索引完成状态安排后续工作。

## 验证场景

- 连续执行两轮扫描，第二轮复用未变化哈希，不新增重复路径记录。
- 增加、修改、删除及重新放回文件后扫描，索引和编号正确更新。
- 目录中同内容的多个旧文件、空目录、非标准文件名都保留。
- 哈希期间文件变化或读取失败，旧哈希失效，目录不执行不完整的缺失清理。
- 扫描执行一半中断后重新执行，保留成功批次并补完剩余文件。
- 同时触发多次 `/scan`，始终只有一个扫描线程任务。
- 扫描期间两个消费者保存同目录文件，扫描结束前不发布正式文件，结束后仅保存一份重复内容。
- 快速去重路径与扫描使用同一目录锁，不能复用失效索引。
- 外部替换同名文件后扫描，旧 Telegram 标识不会误命中新内容，历史结果保留原哈希。
- 等待协程被取消但线程尚未退出时，目录仍被保护，第二次扫描不能开始。
- 旧进度回调延迟到达，不覆盖本次扫描状态或已完成结果。
- 扫描大文件期间 `/status`、接单和进度查询仍可响应。
- 两个消费者可以同时执行文件任务，任务不被重复领取，相册只汇总一次。
- 重启后未过期重试按钮可用，已成功文件不重存，已落盘未提交状态能恢复。

## 实现顺序

1. SQLite 访问层、文件索引和可重复扫描，接入 `/scan` 及目录协调。
2. 接单持久化、默认两个消费者、相册及重试迁移到同一任务流程。
3. 减少复制次数、去掉全局长时间下载锁、改用索引查询统计，并验证故障恢复。

线程取消语义参考 [Python Future.cancel 文档](https://docs.python.org/3.12/library/concurrent.futures.html#concurrent.futures.Future.cancel)；
等待保护参考 [asyncio.shield 文档](https://docs.python.org/3.12/library/asyncio-task.html#asyncio.shield)。
